## **Double-Query-Injection (DQI)**

### **Double Query Injection (DQI)**

**Double Query Injection (DQI)** is an advanced form of **SQL Injection (SQLi)** that exploits database subqueries and aggregate functions to extract data or generate database errors revealing hidden information. It leverages multi-level query structures to trick the database engine into exposing results not otherwise accessible via standard SQLi methods.

---

### **What is Double Query Injection**

Double Query Injection involves embedding one SQL query inside another — a subquery wrapped in a parent query. The outer query processes the result of the inner query, potentially triggering an identifiable error message or conditional logic failure if crafted precisely.

In essence, unlike typical SQLi that inserts malicious input directly into an SQL statement, DQI operates through two query layers. The inner query retrieves unauthorized data, while the outer query manipulates or exposes this data through concatenation, aggregation, or grouping operations.

---

### **How It Works**

A simplified example illustrates the mechanics:

```sql
SELECT COUNT(*), CONCAT((SELECT database()), FLOOR(RAND()*2)) AS a
FROM information_schema.tables
GROUP BY a;

```

When executed, the above query can yield a duplication error such as:

```sql
ERROR 1062 (23000): Duplicate entry 'security1' for key 'group_key'

```

This error message unintentionally reveals information — in this case, the current database name **"security"** — demonstrating how DQI leverages SQL’s internal error handling to extract information.

---

### **Common Building Blocks**

Double Query Injection commonly employs these SQL components:

- **Subqueries:** Queries nested within another query, evaluated first.
- **Aggregate Functions:** Such as `COUNT()` or `FLOOR()`, used to generate meaningful error responses.

# 🔍 What each part does (short)

- `FROM information_schema.tables`
    
    Uses the metadata table that lists all tables visible to the current user — produces one row per table.
    
- `FLOOR(RAND() * 8)`
    
    `RAND()` gives a pseudo-random float in `[0,1)`. Multiplying by 8 => `[0,8)`. `FLOOR(...)` converts to integer in `{0,1,2,3,4,5,6,7}`. Evaluated per row — used to split rows into random buckets (0..7).
    
- `CONCAT(0x3a,0x3a,(SELECT DATABASE()),0x3a,0x3a,FLOOR(RAND() * 8)) AS a`
    - `0x3a` is hex for `:` — repeated gives `::` as delimiter.
    - `(SELECT DATABASE())` returns current DB name (e.g. `armour_db`).
    - Whole `CONCAT(...)` builds strings like `::armour_db::3` (3 = random bucket).
- `SELECT COUNT(*), ... GROUP BY a`
    - `COUNT(*)` counts how many source rows fall into each `a` group.
        - Alias it as `a`.
    - `GROUP BY a` groups by the concatenated string (so groups split by the random bucket). This is the core trick used to force multiple evaluations and infer values (error-based / grouping inference).

## 3) Quick tips while running these

- Run one payload at a time and inspect the **HTTP response body** — error-based payloads return DB info inside an SQL error message (the script currently `die()`s on error).
- If you get no visible error (because of differences in MySQL/PHP versions), try slight variations or increase index (LIMIT N,1) to enumerate further entries.
- To avoid terminal quoting problems, paste the whole `curl "..."` line — don't break it across lines.
- If responses are noisy, check `/var/log/apache2/error.log` for raw DB error text.
